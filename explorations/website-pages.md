## The itch, and the decisions so far

A share link today is `renderPrintDocument()` (`src/lib/print-html.ts`), the same page Save Offline makes: a good document, not a web page. Tyler wants shared items that read like real pages (hero, cards, carousel) plus a simple design system, without making every item carry that weight.

**Decided in conversation:**
- **A bespoke pre-built type, "Website Page"**, not new syntax in every body. Scoping (a `:::` block in an ordinary note gets no layout; its fence lines just drop out of the document render, ADR-284), a canvas that fits the job (theme picker, Preview, share defaults to page), and a smaller ADR. Precedent: `chordpro` as a per-type markdown-family format; `file` (ADR-236) and `passage` (ADR-060) as shipped pre-built types. Likely its own **module** under ADR-272 (`requires: sharing`).
- **Layout lives in the markdown as Pandoc fenced divs**, not `{hero}` / `{slide 1}` tokens. Curly tokens show as literal text in the editor and risk escape churn; "slide" is already taken (ADR-176, the booth-export mark); inferring layout from scattered tokens is fragile. `::: hero` … `:::` degrades as text everywhere, nests (`:::: carousel` > `::: slide`), and pandoc's `.docx` export keeps it as a div.
- **Blocks guess their parts from plain markdown inside them.** In `hero`, the first image is the background, the heading is the headline, a link is the button. In `cards`, each `###` starts a card. The author writes normal markdown, with no list of settings to learn. First set: `hero`, `cards`, `columns`, `carousel` (CSS scroll-snap, no JS), `gallery`, `callout`, `cta`.
- **Design system = a theme made of a few settings**, never per-page CSS: font, accent, radius, density, light/dark as CSS custom properties. ~4 presets + accent picker + a workspace default ("my brand"), overridable per page. Blocks emit classes; the theme supplies the look.
- **Starter sets (Tyler, same day), modeled on Claude Design's design systems.** A theme is three layers the owner can mix and match, each shipped as a short list of curated options:
  - **Design language**, the part that sets the personality: block *variants*, not just colors. Hero full-bleed vs. split vs. plain; cards bordered vs. elevated vs. flat; heading case and weight; radius; spacing; section dividers. Start with ~5: *Editorial* (serif headings, generous whitespace), *Modern* (clean sans, soft radius), *Bold* (big type, full-bleed color blocks), *Warm* (rounded, earthy), *Minimal* (monochrome, hairlines).
  - **Font**, one family per page, not heading/body pairs (Tyler, same day: "we just moved over to Public Sans, it works on its own"). Hierarchy comes from weight, size and tracking, which the design language sets, so one family reads as Editorial or Bold depending on the language. Ship each as a single **variable woff2** (one file covers every weight), five at launch, in this order (Tyler, same day): **Public Sans (the default for new pages and brands**, Tyler: "it ticks all the boxes"), **Classic (Helvetica)**, which ships no file: the stack `"Helvetica Neue", Helvetica, Arial, sans-serif` renders real Helvetica on Apple devices and Arial (its metric match) elsewhere, since Helvetica is a paid license that can't be self-hosted (TeX Gyre Heros is a free, self-hostable clone if Windows viewers ever need the true look); **Montserrat** (wide geometric letters, a natural default for the Bold language; languages that use it get a bit more line height for body text); **Figtree** (friendly, rounded, a natural default for the Warm language); and **Source Serif 4**, so Editorial has a real serif. Inter was considered and cut: it overlapped Public Sans and Helvetica as a third neutral sans. A separate heading font can come later as an advanced override if anyone asks. **Self-host the files** rather than linking Google Fonts: a viewer's request to Google leaks their IP, which undercuts the share page's `no-referrer` / `noindex` posture, and self-hosting keeps the page working offline.
  - **Palette**, four at launch so far: **Slate, Navy, Forest, Dusk** (Tyler, 2026-09-28, after seeing the sample page; Ember, Plum and Mono cut, Mono because it only earns its place on paper). **Each palette has three colors with fixed jobs** so they never compete: a *lead* color (buttons, links, the Bold hero), a *support* color (tinted section bands, card fills, labels), and a small *highlight* (dots, key numbers, one button). Slate = blue / steel gray / sky (teal and amber replaced at Tyler's request); Navy = navy / sky / coral; Forest = green / moss / sunflower; Dusk = indigo / periwinkle / peach (Tyler picked it over Wine, Harbor and Stone). Tyler wants a fifth; Harbor (teal / ocean / coral) and Stone (charcoal / sand / teal) are the standing candidates. Page backgrounds carry a faint tint of the palette (Tyler liked this on Forest). **Every palette ships a light and a dark version** (Tyler: keep the dark options for sure), each contrast-checked.
  - **The picker explains every option** (Tyler, same day): each language, font and palette shows a line or two of design reasoning (what it feels like, what it suits, e.g. "Source Serif: bookish and trustworthy, for long reading, sermons, stories"), so the owner chooses by fit for what they are making, not by guessing from a swatch.
  - Each language picks a default font and palette, so choosing one language is enough; the other two layers are overrides. A saved combination becomes a named **brand** (the workspace default).
- **Sample page and design review (2026-09-28):** [Ledgr Design Languages](https://claude.ai/artifact/NLsmZyq7W6zYdULsuYXByS), source in the session scratchpad. Tyler approved all five languages. Rules from his review: when the hero stacks (Minimal, Editorial, and every language at phone width) **the image goes on top and is short** (a strip, not a block); boxed blocks need real space between them; the picker needs a plain-language **"how they differ" guide** (corners, font feel, color use, image placement, when to reach for it), which the sample page carries as a table. Language defaults: Modern and Minimal = Slate, Bold and Editorial = Navy, Warm = Forest.
- **What pages are for (Tyler, same day):** putting information *out* to people, e.g. a presentation, a CV, a finished project written up for review. So blocks are for showing, and a button is just a link. Collecting input (a "Registration" type with a form) is a separate idea, not part of this feature.
- **Buttons are plain markdown links** (Tyler, same day): inside a `hero` or `cta`, `[Register](https://…)` renders as a button, so the owner just pastes a URL. Bonus that costs little: an @-mention of a **Link item** (`[@Title](ledgr://item/<id>)`) resolves to that item's URL on the page. Mentions of any other item must NOT render as `/items/<id>` on a public page (a stranger gets a login wall and the owner's item id leaks); they fall back to plain text, or to that item's share URL if it has a live one.
- **Two layout mocks (2026-09-28):** [Ledgr Page Layouts](https://claude.ai/artifact/8gZBCXk9BcrUkDqLviJz5U). **Resume**: one note written with blocks (new `profile` and `timeline`, shared `tags`), Modern language. **Magazine** (Tyler: port the Savor devotionals and let people read through them, old-blog style): a page whose sections are **queries**, not typed content. Each section picks a type, then narrows by tag, hand-picked items, or a saved View (`hero` = #featured newest 3, `list` = newest 4 skipping items already shown, `row` = one tag oldest first as a series, `topics` = tag cloud with counts). **Every matched item gets its own article page under the same share link**, with "Keep reading" from shared tags. This makes a Website Page a small multi-page *site*, which is a bigger step than slice 1 and wants its own slice after it.
  - **Privacy fork, settled (Tyler, 2026-09-28): publishing is an explicit act, never a side effect of a tag.** A query over ordinary tags would publish *future* matches (tag a note #featured next month and it is public), and Tyler flagged the mix-up risk directly. Options weighed: a flag-and-approve queue on tag matches (still lets a general tag drive publication), a dedicated "web tag" type or tag namespace (a second tag system to learn and keep straight). **Chosen: a "published on" relation between an item and a Website Page.** Only items with that edge can ever appear on the page; tags, types and Views only *filter and order within* that published set. So a tag on a note can never publish it.
    - Adding: an **"Add to page…"** action on any item (and in the multi-select bulk bar, per the ADR-118 standard) creates the edge; the page canvas can also hand-pick items.
    - Visibility: an item that is published shows a **"Public on: Morning Bread"** chip on its canvas, and the page canvas lists **everything it exposes**, with remove per row.
    - Opt-in automation for people who want a blog that fills itself: a per-page **"automatically add new <type> items"** switch, off by default, labeled as publishing.
    - Removing the edge (or the item going to Trash) takes it off the page; subpage URLs for it 404 like a revoked share.
    - **It is the share system's sibling, and should look like it** (Tyler, same day: "you'd want a publish button anyway… not that different from our current share system"). The item's share panel grows a **Publish** control beside the share link: pick a page, publish, unpublish. The "Public on" chip reuses the shared-item indicator. The edge carries a **published-at** date, which is what a magazine sorts by (not the note's created date), so a devotional written in March and published in October lands as new. Unpublish works like revoking a share link: immediate at the origin, gone from the edge cache within ~60s.
- **Direction (Tyler, 2026-09-28, after the layout mocks missed): capabilities first, starters on top, any starter in any language.** What gets built is the capability set: blocks, **collection sections** (a type + tags, hand-picked items, or a saved View), **subpages** (every item in a collection gets its own page under the share link), an **`embed`** block (YouTube/Vimeo) and **link cards** (a URL or a Link item as a card). Starters (Resume/Portfolio, Magazine, Project showcase) are pre-filled combinations of those, never separate engines. The design language is orthogonal: the mocks lost it by hardcoding a style per layout, and that is the thing not to repeat. Tyler's portfolio ask ("add their work, subpages with an embed of their teaching or a link to their work") is the magazine's collection + subpage capability pointed at Project/Link items. Visual design is out to Claude Design with a brief (2026-09-28); the parser, render seam, type/module and ADR do not wait on it.
- **The document render stays a document.** Print and Save Offline stay byte-identical (ADR share decision); the page render is a second shell. The one change to the document render is ADR-284's: fence lines are stripped, content kept, so a page body prints as clean prose. That strip is dialect-wide (any type's body), while the *layout* render is scoped to the Website Page type. Block parser + page renderer live in core `src/lib/` so the module only adds the shell and the stylesheet.

## "Make a webpage" in the share panel: the fill system
- **It creates a new Website Page item instead of converting the original,** with a relation back to the source note. Copy beats sync: a synced page would overwrite the owner's customizations. A later "Refresh from source" can re-run the fill and ask before replacing.
- **Layouts are slot definitions.** Call them *layouts*, not templates (Ledgr Templates already exist). e.g. Event = `hero` + details `cards` + `cta`; Announcement = `hero` + body + `callout`; Landing = `hero` + `cards` + `gallery` + `cta`. Each slot declares what content it accepts (image, heading, section, image run, link).
- **One filler, two entry points.** The filler classifies the note's content into pieces (leading image + heading, `##` sections, image runs, blockquotes / "Note:" lines, trailing links, everything else) and assigns them to slots.
  - *Guess:* score every layout by how well the note's pieces fill its slots, pick the best, show the pick with a one-tap "try another layout."
  - *User picks:* same filler, fixed layout; unfilled slots get placeholder text, leftover content lands in a plain section so nothing is lost.
- **Deterministic rules, no AI**, so it's free, fast, predictable and explainable ("hero because the note opens with an image and a heading"). "Claude, redo this layout" can be an optional later version over MCP.
- Then the owner customizes on the Website Page canvas with the block tools.

**Slices:** (1) the type + page renderer + `hero`/`cards`/`callout` + one theme + page-mode share; (2) starter sets (languages, fonts, palettes) with the picker and Preview on the canvas; (3) layouts + the filler + the share-panel button; (4) more blocks, `/section` slash command, Tiptap node views that frame each block.
